FastQC notes - RNA-seq reads (GSE52778 airway data), Tutorial 4
Vir Patel

Samples checked: SRR1039508 and SRR1039516, read 1 and read 2 of each
(reports: fastqc_out/*_fastqc.html). All reads are 63 bp, ~49-50% GC.
Total sequences: SRR1039508 = 22,935,521 per mate; SRR1039516 = 27,298,970 (read 1) and 30,043,024 (read 2, before the fix described below).

Summary of FastQC modules
- PASS in all four files: Per base sequence quality, Per sequence quality scores, Per sequence GC content,
  Sequence length distribution, Adapter content.
- Per base sequence content: PASS in all four files.
- Per base N content: PASS except WARN for SRR1039508 read 2 (a few uncalled bases).
- Per tile sequence quality: WARN for SRR1039508 read 1 and FAIL for SRR1039508 read 2 (a few flow-cell tiles with lower quality);
  PASS for SRR1039516.
- Sequence duplication levels: FAIL (SRR1039508 read 1, SRR1039516 both reads) or WARN (SRR1039508 read 2).
- Overrepresented sequences: WARN for SRR1039508 (both reads); PASS for SRR1039516.

Red flags? Should I be concerned?
- The duplication FAILs are expected for RNA-seq: highly expressed transcripts are sequenced many times, and unlike
  genomic DNA these duplicates should not be removed. The overrepresented-sequence warnings in SRR1039508 are most likely
  abundant transcripts, not contamination.
- The per-tile warning/failure in SRR1039508 read 2 and the few N bases point to a small localized quality problem on the
  flow cell; since overall per-base quality passes, I would not discard the sample.
- No adapter contamination was detected and per-base quality passes, so trimming is not needed.

Do the sequences need trimming? No. Adapter content passes and base quality is good along the whole 63 bp read. STAR can soft-clip
low-quality ends during alignment.

Problem found with the read files (not a quality issue)
The prof's script uses `fasterq-dump --split-files`. For SRR1039513, SRR1039516, SRR1039520 and SRR1039521 the _1 and _2 files had
DIFFERENT numbers of reads (e.g. SRR1039513: 16,823,088 vs 43,356,464), because some spots have a 0-length mate; the dump log reported
"reads 0-length". STAR cannot align unequal paired files. I re-ran those four accessions with `fasterq-dump --split-3`
(02b_fastq_dump_fix.sh), which writes only matched pairs to _1/_2 (orphans go to a separate file), and then checked that all eight pairs
have equal read counts before running STAR.
